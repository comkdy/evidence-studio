# 처리량 제약에 맞춘 지식 구축과 질의

SQLite·Markdown·기존 claim·수치·Wiki 이력은 유지한다. 새 schema는 초기화할 때 추가한다. 이 개편은 모델 가중치 학습이나 외부 문헌 자동 수집을 수행하지 않는다.

## 데이터와 실행 순서

1. PDF의 텍스트·위치·메타데이터를 저장하고 로컬 구조 분할과 원문/claim FTS를 반영한다. 이 경로에는 LLM·embedding·Wiki 완성 대기가 없다.
2. 전문가 담당 논문과 조사 질문이 분석 수요를 만든다. `(작업 종류, 대상, 입력 hash)`가 같은 작업은 전문가 간에 공유한다.
3. 원문 구간별 추출 후보 → 정확한 인용·수치·조건 검사 → 별도 모델 검토 → Markdown 렌더링으로 처리한다. 분석 후보를 canonical claim으로 자동 승격하지 않는다.
4. 최초 구축은 작은 묶음부터 시작하고 maintenance가 미분석 구간을 추가 예약한다. 기존 claim 몇 개나 Wiki 한 개를 전체 분석 완료로 간주하지 않는다. 화면에 처리 구간과 미처리 범위를 표시한다.
5. 질문별 비교 자료는 공통 원천 근거에서 만들고 별도 검토를 거친다. 전문가 특화 해석과 사용자 피드백은 출처가 있는 논문 사실과 구분한다. 수요 해제는 기존 공통 문서를 자동 폐기하는 조건이 아니다.

특화 노트의 검토자가 공통 재사용을 명시적으로 승인한 경우에만, 원천 근거에서 공통 주제를 새로 종합하고 다시 검토한다. 특화 문장을 그대로 복사하지 않으며, 공통 주제에서 재승격하는 반복은 없다. 공유 질문에서 비롯된 승격은 원래의 공개 권한을 계속 따른다. 해당 공유가 철회되면 그 질문만 의존하는 준비 자료·특화 노트·공통 승격 자료를 검색과 재사용에서 제외한다.

원문 구간 hash, 모델 배포 revision, 작성 지침, 전문가 범위, 자료 의존 관계를 저장한다. 구간이 바뀌면 해당 추출을 갱신하고 영향을 받는 종합만 다시 준비한다. 답변 캐시는 보수적으로 무효화하므로 관련 없는 색인 변화에도 miss가 발생할 수 있다. 이는 잘못된 재사용을 줄이기 위한 초기 정책이다.

관측·추정·해석의 분류를 후보에 저장하며 분류가 빠진 후보는 `분류 미확인`으로 표시한다. 검증기는 인용 위치와 수치·단위, 일부 명시적 조건 표현을 검사한다. 과학적 타당성과 조건의 완전성까지 증명하는 검사는 아니므로 독립 내용 검토와 사람의 판단을 대신하지 않는다. 검증 정책이 바뀌면 이전 정책의 자동 생성 Wiki도 재검토 전까지 재사용하지 않는다.

명시적 의미 기반 재색인은 `prepare_index` 또는 `prepare_document_index`로 원문 snapshot과 embedding을 쓰기 트랜잭션 밖에서 준비하고, `validate_prepared_input`으로 원문이 그대로인지 확인한 뒤 짧은 트랜잭션에서 `reindex_document(prepared=...)`로 발행한다. 의미 기반 계산을 DB 쓰기 트랜잭션 안에서 수행하지 않는다.

## 사용자 질문

`POST /api/pilot/research-requests`는 `question`, `expert_ids`, `visibility`(`private` 또는 `team`), 선택적 `selection`, `history_run_ids`, `report_id`·`report_section_id`·`report_revision`을 받는다. 원격 모델을 부르지 않고 로컬 근거·요청 ID·상태를 반환한다. 화면은 동일 요청을 조회해 상세 답변을 이어 표시한다. 전문가 추천은 프로필·용어·검색 점수로 처리한다. 과거 대화나 보고서를 사용하는 요청은 소유권을 검증하고 비공개로 제한하며 공통 개선 수집에서 제외한다.

| API | 기능 |
|---|---|
| `GET /api/pilot/research-requests` | 본인 질문 목록; `visibility=team`은 공유 목록 |
| `GET /api/pilot/research-requests/{id}` | 근거·단계·최종 답변 조회 |
| `POST /api/pilot/research-requests/{id}/cancel` | 본인의 대기/진행 질문 취소 |
| `PATCH /api/pilot/research-requests/{id}/visibility` | 본인의 공유 상태 변경 |
| `GET /api/pilot/knowledge/progress?expert_id=...` | 분석 범위·대표 질문·미해결 항목·개선 기록 |
| `POST /api/pilot/knowledge/questions` | 전문가에게 조사 질문 등록 |
| `POST /api/pilot/knowledge/feedback` | 요청에 대한 보완 의견 등록 |

기존 동기 `/api/pilot/ask`는 호환용으로 유지한다. 비동기 결과의 소유권과 공유 인용 접근을 서버가 검사한다. 기존 개인 answer run은 계속 소유자 전용이며, 공유 화면에서는 명시적으로 공유한 요청의 인용만 노출한다.

화면 이동·새 대화는 조회만 중지하고 서버 작업을 취소하지 않는다. 명시적인 답변 중지만 취소 API를 호출한다. 서버 이력에서 진행 질문을 다시 열어 이어 볼 수 있다. 대화 옆 보고서 편집은 기존 `/reports/{id}/edit-stream` 경로를 유지한다. 요청 목록은 `summary=true`로 본문을 생략하고, 선택한 질문에서만 근거·답변 전체를 가져온다.

배경 조사 계획·보완 검색이 완료되어 현재 근거 hash와 일치하는 준비 자료가 있으면 답변 생성과 내용 검토의 2회 호출로 처리한다. 새로운 조사가 필요한 질문은 계획·보완 검색을 추가한다. 준비 자료는 검토된 완성 답변이 아니므로 둘을 구분해 표시한다. 동일 소유자의 **동일 질문 문자열·전문가 범위·조건·근거·모델 설정**에 유효한 검증 답변이 있으면 새 소유자별 실행 snapshot을 만들어 재사용한다. 유사 질문에는 준비 근거만 재사용하며 완성 답변을 의미 유사도로 재사용하지 않는다.

## 큐와 모델 자원

`work_tasks`, `work_dependencies`에 우선순위·중복 키·완료 단계·재시도·실행 lease를 저장한다. 정상 완료된 작업은 재사용한다. 실패 작업을 반복 예약하지 않으며, 명시적 수요 복원 경로만 재개할 수 있다. 취소나 lease 만료 후의 worker는 checkpoint/최종 발행 권한을 잃는다. 요청 취소가 다른 전문가가 사용하는 공유 선행 작업까지 취소하지 않는다.

우선순위는 사용자 답변(0), 답변 근거(10), 사용 중인 자료 갱신(20), 예약 질문(30), 전문가 구축(40), 탐색 질문(50), 정기 검토(60) 순이다. 답변과 배경 dispatcher를 분리하고 배경 dispatcher는 하나만 둔다. 모델 호출은 `model_waiters`의 자원 그룹별 한 슬롯을 공유한다. 배경 호출 사이에 사용자 작업에 양보한다. 이미 서버에 전달한 HTTP 요청의 GPU 계산을 즉시 중단하거나 선점할 수 있다고 가정하지 않는다.

기존 수동 Wiki 갱신 요청도 공통 배경 큐로 전달한다. 정기 검토는 하루 예산 내에서 한 단계당 모델 호출 한 번으로 나누며 다음 단계 전에 다른 작업에 양보한다. 현재 기본 예산은 회차당 최대 12회·입력 60,000자이며, 긴 문서는 검사한 위치부터 이어 간다. 서버 호출이 실패하면 남은 연속 호출을 멈춘다.

`LLM_ANSWER_*`, `LLM_BACKGROUND_*`, `LLM_REVIEW_*`는 각각 답변·분석·검토 모델 설정이다. 생략한 값은 기본 설정을 상속한다. 역할별 `_MODEL`, `_CONTEXT_TOKENS`, `_TOKENIZER_PATH`, `_RESOURCE_GROUP`, `_DEPLOYMENT_REVISION`, `_MAX_OUTPUT_TOKENS`를 지정할 수 있다. URL·키는 기존 공유 연결 `LLM_BASE_URL`·`LLM_API_KEY`를 사용한다. 기본 자원 그룹은 `shared`이며 전체 동시 호출 기본 상한도 1이다. 실제 하드웨어 분리가 확인된 경우에만 그룹을 다르게 설정한다. 모델명은 같지만 배포 가중치가 바뀌면 revision을 변경한다. GLM/Qwen 중 어느 것이 빠른지는 코드에서 가정하지 않는다.

앱 프로세스가 실행 중일 때 worker가 동작한다. 24시간 운영에는 사내 서비스 관리자로 프로세스를 상시 실행해야 한다. 현재 앱은 한 서버 프로세스 구성을 유지한다. 비동기 요청과 작업은 재시작 후 DB에서 이어 처리한다.

기존 설치에서는 처음 시작할 때 빠진 로컬 QA 색인과 활성 전문가 수요를 보충한다. 알려진 내부 자동 사유와 일치하는 대기 중 전체 Wiki 예약만 전환 완료로 표시하고 이력을 남긴다. 수동·관리자·사유가 불명확한 요청은 보존해 공통 큐로 실행한다. 원문·claim·Wiki·개인 실행 기록을 삭제하지 않는다.

## 지속 개선과 공개 범위

질문자는 출처가 있는 원문으로 탐색 질문을 만들고, 사용자 등록 질문과 팀 공유 질문을 우선 처리한다. 비공개 질문은 학습 목록에 들어가지 않는다. 공유 철회 시 해당 질문만을 근거로 하는 공유 준비 자료와 수요를 비활성화한다. 사용자 의견은 확인 전에는 미검증 참고 정보이다.

전문가별 새로운 자동 탐색 질문은 하루 최대 5개이다. 질문별 동일 원천 자료 버전의 보완 시도는 최대 2회이며 자료가 바뀌지 않으면 미해결 질문을 계속 반복하지 않는다. 새로운 논문이나 원문 교정이 있으면 다시 조사할 수 있다. 검색 누락, 추출 누락, 조건 부족, 충돌, 보유 문헌으로 해결 불가를 나누고 해결 불가는 추가 문헌·팀 정보·실험 필요로 남긴다.

원문 검사와 독립 모델 검토 통과는 `자동 검토`이다. 사람 검토 완료와 같지 않다. 충돌·검증 실패 자료는 승인된 지식으로 발행하지 않는다. 전문가 화면의 대표 질문 준비 상태도 근거 준비와 답변 검증을 구분한다.

## 검증과 운영 측정

회귀 테스트는 임시 DB·합성 논문·모의 모델을 사용한다. 원문 검색의 Wiki 독립성, 구간별 재개, 전문가 간 중복 억제, 새 근거/조건/설정 변경의 캐시 무효화, 비공개 자료 제외, 공유 철회, 취소·lease·우선순위를 검사한다. 사내 모델 지연과 과학적 답변 품질은 이 테스트만으로 판정할 수 없다.

`research_request_metrics`는 첫 근거와 최종 답변 시간을, `model_call_metrics`는 호출 역할·서버 처리/대기 시간·사용량을, `work_stage_metrics`는 단계별 대기·실행 시간을 기록한다. 질문 본문이나 API key를 측정 로그에 복사하지 않는다.

```powershell
.\.venv\Scripts\python.exe -m backend.throughput_report --database data\evidence-studio.sqlite3 --output artifacts\throughput.json
.\.venv\Scripts\python.exe -m backend.evaluate_research --database data\evidence-studio.sqlite3 --cases team-research-cases.json --output artifacts\retrieval.json
```

첫 명령은 읽기 전용으로 p50/p95·호출 수·실패·검증 상태를 집계한다. 두 번째는 기존 검색 평가 도구이며 정답 논문/근거 회수율을 비교한다. 동일 논문·고정 질문·동일 모델·배경 부하를 맞추고 충분한 반복 표본을 수집한다. 온도·전압·시료가 다른 비교, 새 반례, 답할 수 없는 질문을 포함한다. 분야 전문가가 인용·수치·조건·반례·미응답의 정확성을 별도로 평가해야 한다. 이번 구현 과정에서 사내 운영 p50/p95 향상을 실측했다는 뜻은 아니다.

2026-10-20 통합 점검에서 최신 대화·보고서·공유 모델 연결 설정을 유지하며 전문가 생성 → 담당 논문 → 공통 Wiki → 질문하기의 연결을 확인했다. 새 담당 논문이나 전문가 범위 변경은 영향받는 특화 노트를 다시 예약하며 기존 원문 분석을 재사용한다. 논문 상세 화면은 구조화된 claim 유무와 별도로 원문 분석 구간·검토 상태·공통 Wiki·담당 전문가를 표시한다. 가져오기 CLI는 원문 색인과 분석 수요까지만 등록하고 대기 중인 전체 Wiki 작업을 직접 실행하지 않는다.

합성 논문과 임시 서버를 사용한 브라우저 점검에서 전문가 생성·담당 논문 이동·전문가를 선택한 질문 제출·초기 원문 표시·화면 이동 후 답변 이어 보기·명시적 취소·팀 공유 질문 수집을 확인했다. 개인 대화 문맥을 포함한 후속 질문은 비공개로 유지한다. 기존 운영 DB와 사내 모델은 이 검증에 사용하지 않았다. 운영 적용에는 서버 재시작이 필요하며 사내 지연 수치는 별도 측정해야 한다.

최종 검증 결과: Python 회귀 457개와 프런트엔드 테스트 60개 통과, TypeScript 검사와 Vite 프로덕션 빌드 성공. 브라우저 콘솔 오류 없이 위 연결을 확인했다. Windows 진단 결과 파일의 일시적 교체 잠금도 재현해 제한적으로 재시도하도록 수정했으며, 격리 차단과 지속적인 권한 오류는 실패로 유지한다. 테스트 실행 시간은 로컬 검증 환경의 값이며 사내 모델의 응답 지연을 나타내지 않는다.
