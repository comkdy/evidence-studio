# Evidence Studio — Markdown Wiki 운영 안내

2026-10-14. 이 문서는 현재 Wiki 실행 구현의 기준이다. 질의·답변의 상세 기준은 [연구 QA](RESEARCH_QA.md), 비교 측정은 [검색 평가](RESEARCH_EVALUATION.md)를 함께 읽는다. 저장 구조는 [DB 구성](DATABASE_PLAN.md)과 함께 읽는다.

## 저장 구조와 책임

```text
raw/                         원본 PDF
data/evidence-studio.sqlite3  논문·claim·수치·조건·정확한 인용 위치
backend/prompts/wiki_policy.md  ingest·답변·lint의 공통 작성 지침 원본
wiki/
  AGENTS.md                  공통 작성 지침으로 안내하는 짧은 링크
  index.md                   공통 지식과 전문가 Wiki의 시작점
  log.md                     불변 버전 기록으로 재구성하는 변경 이력
  lint.md                    최근 정기 점검 결과
  common/sources/*.md        기존 정리 내용과 claim·조건을 재사용한 원천 지식
  common/topics/*.md         여러 논문을 연결하는 공통 주제 지식
  experts/<id>/index.md      전문가 개요와 담당 공통 지식의 연결 목록
  experts/<id>/notes/*.md    필요할 때 요청한 전문가 특화 주제
  .history/                  게시한 Markdown의 불변 버전
  .reports/                  회차별 lint 결과
```

**Wiki 본문의 원본은 실제 Markdown 파일이다.** DB의 `wiki_files`는 경로·hash·근거·버전 정보이고 `wiki_fts` 및 `retrieval_units`는 재생성 가능한 검색 캐시다. 파일을 읽는 API는 DB의 옛 본문을 대신 보여주지 않는다. `knowledge_pages`와 `knowledge_links`는 기존 구조화 기록을 보존하기 위해 유지한다. 초기 마이그레이션 뒤 앱의 Wiki 조회는 Markdown을 사용한다.

원천 지식은 전 전문가가 공유한다. 신규 전문가 생성 자체에는 LLM 분석 호출이 필요하지 않다. 편입 기준으로 담당 논문을 고르고, **모든 근거 논문이 담당 범위에 속하는 공통 Wiki만** 연결한다. 그 전문가에게만 필요한 특화 해석은 명시적으로 요청한 주제에 한해 작성한다. 공통 종합의 일부 근거만 담당하는 전문가는 그 종합을 사용하지 않고 자기 논문의 원천 지식을 검색한다.

전문가 생성 미리보기의 **재사용할 공통 Wiki**는 현재 Markdown 원장의 `source`·`topic` 중 담당 범위에 속하고 본문 및 의존 파일이 유효한 문서 수다. `awaiting_llm` 문서도 포함하므로 종합 완료 건수를 의미하지 않는다. 기존 전문가의 특화 노트·자동 목차·내부 분할 문서는 포함하지 않는다. 생성 직후 공통 지식 조회와 질의가 가능하며 전문가 목차를 만드는 백그라운드 작업을 기다릴 필요가 없다.

화면의 Wiki 목록·전문가별 Wiki 수와 질의 검색 대상은 `source`·`topic`·`specialization`이다. `expert_index`와 내부 `source_part`·`topic_part`는 보관 및 문서 구성에 사용하며 일반 목록·검색에서 제외한다. 원천이나 의존 문서가 보관 처리되거나 오래되면 연결 문서도 질의 근거로 사용할 수 없다. 사용 중지된 전문가는 Wiki·질의에서 제외하되 라이브러리의 담당 논문은 계속 열람할 수 있다.

## 공통 작성 지침과 index 관리

관리자가 수정할 작성 지침은 `backend/prompts/wiki_policy.md` 하나다. `wiki/AGENTS.md`는 이 파일을 가리키며 규칙을 복사하지 않는다. `wiki_compile.txt`, `wiki_answer.txt`, `wiki_lint.txt`는 작업별 역할과 JSON 출력 규약만 추가한다. `backend/wiki_policy.py`가 실제 호출의 system message를 구성한다. 논문·질문·기존 Wiki에서 발견한 지시문은 작성 규칙으로 사용하지 않는다.

- 답변은 매 요청 때, ingest와 lint는 각 작업 시작 때 원본 파일을 다시 읽는다. 파일이 없거나 비어 있으면 지침 없이 모델을 호출하지 않는다. 답변은 안내와 함께 검색 근거만 반환하고, 갱신·점검은 오류로 중단한다.
- 하나의 ingest/lint 작업은 동일한 지침 snapshot을 사용한다. 도중에 지침을 편집하면 다음 작업부터 적용한다. 앱은 60초 간격으로 ingest 지침 변경을 확인하여 갱신 작업을 예약한다. 즉시 적용하려면 `sync`를 실행한다.
- 작성 지침과 작업별 프롬프트의 hash를 생성 입력에 포함한다. 지침 변경은 종합 문서의 재작성 대상 판정과 lint 검토 캐시를 무효화한다. 기존 canonical DB와 단순히 재사용한 논문별 원천 지식은 다시 추출하지 않는다. 지침을 크게 바꾸면 영향받는 종합 문서 전체에 재작성 비용이 들 수 있다.
- 종합 문서 frontmatter의 `refs.policy_hash`와 `refs.prompt_hash`로 적용된 지침을 식별한다. lint 보고서에도 공통 지침 hash를 기록한다. hash는 적용 내용의 식별자이며 과학적 검증 완료를 뜻하지 않는다.
- `wiki/index.md`와 전문가별 `index.md`는 코드가 생성하는 목차다. 문서의 추가·갱신·제외와 함께 링크를 관리한다. 전체 목차는 전문가·공통 주제·논문별 원천 지식으로 나누고 상태·버전·근거 논문 수·갱신일을 표시한다. 전문가 특화 노트는 해당 전문가 index에 연결한다.
- 내용이 같으면 전체 index와 log를 다시 쓰지 않는다. lint는 index 누락·현재 목록과의 불일치를 검사하며, `sync`가 이를 복원한다. index는 사실의 출처가 아니며, 질의 때 전체 목차를 LLM에 전달하지 않는다. 목차 생성에는 LLM 호출이 없다.

공통 지침 파일도 앱 소스와 함께 사내로 가져간다. Wiki 폴더만 별도로 옮기면 지침 링크가 끊어질 수 있다.

## 빈 배포본에서 시작하기

공개 배포본에는 운영 DB·Wiki·원본 PDF가 없다. 사내 설정을 채우고 앱을 실행하면 빈 DB와 기본 설정을 초기화한다. raw 폴더에 PDF를 추가하면 원문 추출·분류·공통 Wiki 갱신으로 이어진다. LLM 미연결 상태의 awaiting_llm 문서는 종합 완료로 표시하지 않는다.

claim·수치·조건을 SQL 원장에 자동 추출하는 LLM worker는 별도 구현 범위다. 현재는 검증된 JSON을 pilot_curate로 가져오며, Wiki가 원문을 읽어 생성한 설명을 자동으로 SQL claim으로 간주하지 않는다. 기존 원장에 claim이 있으면 이를 우선 재사용하고, 없으면 정확한 원문 구간을 근거로 Wiki를 구성한다.

wiki 폴더는 Git에서 제외한다. 향후 운영 데이터를 이관할 때는 DB·Wiki 전체·원본 PDF를 일관된 시점으로 백업하고, 데이터 없는 앱 소스 배포와 구분한다.

## 갱신과 비용 통제

- 수동 갱신은 **전문가 설정의 관리자 전용 기능**이다. `공통 Wiki 갱신`은 공통 원천·주제 Wiki와 공통 검색 색인만 처리하고 전문가 전용 문서는 재작성하지 않는다. 각 카드의 `Wiki 갱신`은 현재 공통 Wiki를 재사용해 선택한 전문가의 특화 노트·index와 해당 전문가의 검색 색인만 처리한다. 다른 전문가 문서·버전·검색 색인은 유지한다. 전체 목차와 변경 이력은 현재 유효한 문서를 반영한다.
- 공통 갱신 때문에 의존 근거가 달라진 특화 노트는 해당 전문가 갱신 전까지 검색에서 제외한다. 전문가 갱신 시 필요한 공통 원천·요청 주제가 누락되거나 오래되었으면 공통 Wiki를 먼저 갱신하라는 오류를 남긴다. 선택한 범위 밖을 자동으로 재작성하지 않는다. 변화가 없는 입력은 기존 파일과 LLM 결과를 재사용한다.
- API는 `POST /api/pilot/wiki-maintenance/common`, `POST /api/pilot/experts/{id}/wiki-refresh`, `GET /api/pilot/wiki-maintenance/jobs/{job_id}`이며 모두 관리자 전용이다. 기존 전체 수동 재시도 경로는 관리자에게 410, 그 외에는 403을 반환한다. 화면은 각 요청의 대기·실행·완료·실패를 표시한다.
- `wiki_jobs.scope`는 자동 작업의 `all`, 수동 작업의 `common` 또는 `expert`이고 `expert_id`로 개별 대상을 보존한다. 같은 범위의 대기 요청만 합치며 서로 다른 범위의 작업은 따로 실행·기록한다. 한 요청의 실패가 다른 요청의 성공을 취소하지 않는다. 기존 DB의 작업은 `all`로 이관한다.
- 앱 실행 중 `raw/`의 새 PDF를 **60초 간격**으로 확인한다. 감시·논문 ingest·Wiki 갱신을 별도 worker로 실행하므로 Wiki LLM 호출 중에도 새 파일을 발견·대기열에 등록한다. 수정 후 5초 이상 지난 파일을 처리하며, 추출 전후 크기·수정 시각·SHA-256으로 복사 중 변경을 다시 확인한다. 기존 경로의 PDF를 덮어쓴 경우 자동 대체하지 않는다. OCR이 필요한 페이지는 먼저 확인해야 한다.
- `processing_tasks`에 논문·신규 전문가 작업을, `raw_watcher_status`에 마지막 폴더 확인 시각을 기록한다. 논문 원장과 Wiki 작업 ID를 연결해 대기·진행·완료·문제 발생·원문 검토·LLM 연결 대기를 구분한다. 신규 전문가 기록은 전문가 생성 트랜잭션에 함께 저장한다. 중단된 논문 작업은 서버 재시작 시 재개하며 SHA-256 중복 검사를 유지한다. 실패한 파일은 내용이 바뀌면 다시 처리하며 같은 실패를 매번 반복하지 않는다.
- 왼쪽 하단 `작업 현황`은 기존 논문 수 표시를 대체한다. 기존 `확인 필요 N페이지` 링크로 자료 현황을 열면 작업 상태와 원문 검토 목록을 함께 본다. `/api/pilot/processing`은 인증된 일반 사용자도 읽을 수 있고, 파일 경로나 API 설정을 노출하지 않는다. 화면은 5초마다 상태를 읽되 숨겨진 탭에서는 멈추며, 최대 12건만 표시한다. 이는 폴더의 60초 감시 주기와 별개이다.
- 현재 폴더 감시는 기본 로컬 DB와 **서버 프로세스 1개**를 기준으로 실행한다. 서버를 종료하면 감시도 멈춘다. 사내 다중 프로세스 배포 시 감시·논문 worker를 단일 서비스/공유 작업 큐로 분리해야 한다.
- 새 논문 적재·구조화 근거 추가·전문가 생성/수정/삭제와 같은 DB 트랜잭션에 Wiki 갱신 작업을 함께 기록한다. 여러 입력은 하나의 대기 작업으로 합친다.
- 단일 작업 lease로 동시 갱신을 제한한다. 중단된 작업은 재시작 시 재개하며, 실패한 작업은 오류를 남기고 관리자 재시도 또는 CLI `sync`로 다시 실행한다.
- 기존 claim·수치·조건이 있는 논문은 그대로 재사용한다. 미구조화 논문은 추출된 원문에서 정확한 인용을 확인하며 공통 지식을 작성한다. 이때 생성한 지식은 Wiki의 원문 기반 진술이며, 정식 canonical claim을 추가했다고 간주하지 않는다.
- 자료·프롬프트·모델 fingerprint가 같으면 LLM 호출과 파일 재생성을 건너뛴다. 변경된 공통 주제와 연결된 특화 노트만 다시 종합한다. 전문가 수만큼 원문을 반복 분석하지 않는다.
- 원천 데이터 캐시는 DB 트리거의 revision으로 무효화한다. 질문마다 PDF와 모든 claim을 다시 불러오지 않으며, 전문가만 추가해도 원천 캐시는 유지한다. Markdown은 선택한 문서와 근거 의존 파일만 확인하고 읽기 캐시를 사용한다.
- 전문가 삭제는 공통 지식에 영향을 주지 않는다. 전문가 전용 파일은 조회·질의에서 즉시 제외하고 이력으로 보관한다. 설정·삭제 복구가 가능한 기존 제품 동작을 유지한다.

## 원문 텍스트 검토와 보완

- 자료 현황의 경고는 내용의 과학적 오류가 아니라 **텍스트 추출 부족 또는 문자 깨짐**을 뜻한다. 문제 페이지 번호·추출 문자 수·깨진 문자 주변 구절을 보여 주며 PDF와 대조한다. 사용자는 본문/caption 누락·읽기 순서, 수치·부등호·위첨자·단위, 표의 parameter/값/조건 관계를 확인한다.
- `텍스트 보완`은 원본에 맞춘 텍스트 또는 별도 OCR 결과를 저장한다. `원문과 일치함 확인`은 추출문을 그대로 검색에 편입하며 깨진 문자/페이지 번호만 있는 입력은 허용하지 않는다. `검색에서 제외`는 빈 페이지 등 검색 불필요 페이지를 경고 목록에서 정리하되 원본 PDF를 보존한다. 검토 이력에서 `다시 검토`하거나 텍스트를 다시 보완할 수 있다. 자동 OCR 재실행은 아직 연결되어 있지 않다.
- 관리자·슈퍼 유저(`manage_knowledge`)는 반영할 수 있다. 일반 유저는 `page_review_requests`에 수정안을 남기며, 관리 권한을 가진 사용자가 원문을 확인하고 반영/반려한다. 새 SSO 사용자는 기존 자동 등록과 동일하게 일반 유저 권한을 따른다. 모든 변경은 원본 대조 확인과 사유를 요구한다.
- `pages`는 현재 검색용 텍스트를 보유하고 `page_review_changes`는 변경 전후 텍스트·상태·추출 방식과 인용 offset 이동을 불변 기록으로 보유한다. 최초 추출문, 요청자, 처리자, 사유, 시각을 다시 확인할 수 있다. 페이지 revision과 요청 UUID로 동시 수정 충돌·중복 저장을 방지한다. 기존 PDF의 bytes와 SHA-256, canonical claim·수치·조건은 바꾸지 않는다.
- 기존 evidence 인용문을 바꾸거나 매칭 위치가 모호한 수정은 거절한다. 인용문이 그대로 유지되면 정확한 offset만 이동하고 이전 offset을 이력에 남긴다. 인용된 페이지는 제외/검토 재개로 비활성화할 수 없다. 과학적 claim 자체의 교정은 이 텍스트 검토 기능의 대상이 아니다.
- 텍스트·검토 이력·원문 검색 chunk/FTS 갱신은 하나의 트랜잭션이다. embedding 등 검색 갱신이 실패하면 모두 롤백한다. 성공하면 관련 Wiki·통합 검색 갱신 작업을 함께 기록한다. 수정한 원문은 passage 검색에 활용되며 canonical claim을 자동 생성한 것으로 표시하지 않는다. 이미 claim을 선별한 논문의 공통 Wiki는 기존 claim·수치·조건을 계속 재사용한다.
- API: `GET/POST /api/pilot/page-reviews/{page_id}`, 관리자·슈퍼 유저용 `POST /api/pilot/page-review-requests/{request_id}/decision`. `excluded` 페이지는 chunking과 원문 답변 근거에서 제외하며, 미해결 검토 건수에도 포함하지 않는다.

## 질의 흐름

1. 담당 지식 검색 결과와 전문가 개요로 추천한다. LLM이 연결되면 작은 전문가 프로필 목록을 입력으로 추천한다. 미연결/오류 시 검색 기반 추천을 표시한다.
2. 선택한 활성 전문가의 담당 논문 합집합 안에서 키워드 검색과 vector 유사도 검색을 수행한다. 한국어 전문 용어를 공통 용어집으로 확장한다. Wiki·canonical claim·원문 근거가 검색 대상이다.
3. 결과를 RRF로 통합하고, 답변 검색에서는 설정된 reranker로 최대 60개 후보를 재정렬한다. 필요한 Wiki 부분·claim·수치·조건·원문 구절만 선택한다.
4. 직접 검색된 claim·원문을 우선하고 원문 검색 구간의 상위 문맥을 확장한다. 같은 논문의 반복에 제한적인 순위 패널티를 적용하고 조건이 잘린 claim 대신 온전한 근거를 선택한다. Wiki는 본문과 연결 원천이 함께 남은 예산에 들어갈 때만 추가한다. 근거 예산은 기본 32,000자·심층 48,000자다. 전문가별로 근거 본문을 복제하지 않는다.
5. 질문은 심층 분석으로 처리한다. 계획·충분성 검토·답변·진술별 검토를 최대 4회 호출하며 원질문 포함 최대 6개 질의로 보완 검색한다. 합집합의 종합 판단을 먼저 제시하고 전문가별 관점에는 각각의 허용 evidence ID만 사용한다.
6. Wiki 단독 인용, 잘못된 인용구, 확인되지 않은 수치·지원 단위 조합을 거부한다. 사실·해석·가설·실험 제안을 구분한다. 답변 준비 중 근거나 담당 범위가 바뀌면 재질의를 요청하고, 모델 미설정·검토 실패 시 확인 가능한 검색 근거만 반환한다.

전문가가 여러 명일 때 모델 호출을 독립 프로세스 여러 개로 만들지 않는다. 전문가는 범위·개요·지속 지식을 가진 논리적 역할이다. 과학적 함의가 근거에서 실제로 도출되는지까지 코드가 증명하는 것은 아니므로 원문 및 사람 검토가 여전히 필요하다.

개인/팀 대화 목록은 기존 브라우저 시제품 동작을 유지한다. 별도로 답변 당시 근거와 실행 과정을 서버에 보존하며 요청 소유자만 조회한다. 이 기록은 검색 색인이나 Wiki의 입력이 아니다. 브라우저 대화를 삭제해도 서버 기록은 지워지지 않는다. 질문 빈도 집계와 검증된 답변의 자동 FAQ 승격은 아직 구현하지 않았다.

## 주기적인 lint

앱 실행 중 24시간마다 수행한다. 종료된 앱을 대신해 OS 서비스를 설치하지 않는다. 재시작하면 마지막 실행 시점에 따라 밀린 점검을 확인한다.

- 코드: 파일 hash, frontmatter, 근거 claim, 정확한 원문 인용, PDF/Markdown 링크, 전문가 범위, 원천/의존 문서의 갱신 상태를 검사한다.
- LLM: 변경 문서를 우선하여 근거보다 과장된 설명, 조건 누락, 측정과 추정 혼동, 모순 등을 검토한다. 근거로 연결된 claims·수치·조건을 함께 제공한다.
- 기본 예산: **한 회차 최대 12회 호출, 검토 본문·근거 합계 60,000자**. 변경 없는 문서는 최근 검사 결과를 재사용하고 30일이 지나면 오래된 순서로 순환 검사한다. 이는 모든 문서가 정확히 30일마다 검사된다는 보장이 아니다. 밀린 문서는 다음 회차로 이월한다.
- 긴 문서는 진행 위치를 저장하여 다음 회차에서 이어서 검사한다. 사내 LLM 미설정·오류·예산 소진은 `partial`로 기록한다. 수행하지 않은 내용 점검을 성공으로 표시하지 않는다.
- lint는 **검토 의견만 남긴다**. 내용의 자동 수정이나 논문 근거 변경은 하지 않는다. 각 보고서는 `.reports/`에 남고 `lint.md`는 최근 결과를 가리킨다.

## 사내 연결

`.env.example`을 참고한다. 키는 백엔드에서만 읽으며 로그와 Markdown에 저장하지 않는다.

- LLM: Bearer 인증, `{model,messages}` → `choices[0].message.content`. `LLM_BASE_URL`은 기본 경로 또는 `/chat/completions` 전체 URL이다.
- Embedding: 사용자가 확인한 전체 `/embedding` URL, `{input:text,model}` → `data[0].embedding`. 한번에 한 문자열을 보낸다. 모델/내용이 달라진 검색 vector만 다시 만든다.
- Reranker: `EMBEDDING_API_KEY`를 그대로 재사용한다. URL은 그대로 호출한다. 기본 어댑터는 `{model,query,documents}` → `results[{index,relevance_score}]` 또는 `[{index,score}]`. **사내 reranker의 실제 요청 형식은 아직 확인되지 않았으므로 연결 시 대조해야 한다.** 오류 시 결합 검색 순위로 돌아가며 알림을 남긴다.

사내 LLM/embedding/reranker의 품질과 성능은 아직 검증하지 않았다. 로컬 HTTP 테스트 서버와 대체 모델로 프로토콜·잘못된 인용 거부·검색 범위·증분 처리·lint 예산을 검증했다. 설정 후 재시작하면 최초 지식 종합과 vector 색인 생성이 백그라운드에서 실행될 수 있다. Wiki는 모델별 context와 출력 여유로 요청을 검사한다. 로컬 tokenizer가 없으면 보수적인 UTF-8 byte 추정이며 실제 token 수와 다르므로 사내 모델의 규격을 확인한다.

## 운영 명령과 파일 편집

프로젝트 루트에서 실행한다.

```powershell
.venv\Scripts\python.exe -m backend.wiki_engine sync
.venv\Scripts\python.exe -m backend.wiki_engine lint
.venv\Scripts\python.exe -m backend.wiki_engine lint --no-llm
.venv\Scripts\python.exe -m backend.wiki_engine adopt <Wiki-ID>
```

Markdown 직접 편집은 자동으로 덮어쓰지 않는다. 파일과 게시 버전이 달라지면 해당 문서와 의존 문서의 사용을 막는다. 작성 규칙과 기존 근거를 유지하여 편집한 뒤 lint/adopt로 반영한다. adopt는 frontmatter의 근거·범위·revision 변경을 허용하지 않고, 본문 변경만 새 이력에 기록한다. 새 지식의 과학적 타당성을 자동 승인하지 않는다. 이후 관련 공통/전문가 연결을 갱신한다.

관리자 또는 슈퍼 유저가 특화 노트를 요청하는 API:

```text
POST /api/pilot/experts/{expert_id}/wiki-topics
{"title":"Retention과 power의 trade-off","source_ids":["담당 공통 Wiki ID"]}
```

최대 6개 공통 Wiki를 선택하며 담당 밖 근거는 거부한다. 작업은 대기열에서 수행한다. 특화 노트의 자동 대량 생성이나 별도 관리 화면은 추가하지 않았다. 조회 `/api/pilot/wikis`, 원본 `/api/pilot/wiki-files/{id}/markdown`, 버전 `?revision=N`, 점검 상태 `/api/pilot/wiki-maintenance`, 관리자 재시도 `POST /api/pilot/wiki-maintenance/retry`를 제공한다.

## 현재 규모의 한계와 다음 판단 기준

SQLite vector 검색은 담당 범위 내 exact cosine 방식이다. 현재 자료를 시범 운영하기 위한 구현이며, 대규모 ANN 성능을 보장하지 않는다. 원천 캐시는 갱신 후 한 번 전체를 읽고, 갱신 계획 및 검색 캐시 대조도 전체 metadata를 순회한다. 논문이 크게 늘면 paper별 변경 버전/작업 분리와 pgvector HNSW 같은 ANN 저장소로 옮길 수 있도록 검색 모듈을 분리했다.

실제 사내 질문 세트로 원천 검색 중심 답변과 Wiki 활용 답변의 token, 지연, 근거 정확도, 미응답률을 비교한다. Wiki가 자주 재사용되는 주제부터 확장한다. 사용자별 실행 snapshot은 구현했으며, 사내 SSO 연결·서버 대화 동기화와 보존/삭제 정책·다중 서버 작업 관리·운영용 OCR은 후속 범위다.

## 논문 길이와 모델 역할에 따른 작성

원문 전체와 지침·인용 metadata가 모델 입력 한도 안에 들어가면 한 번의 호출로 논문 원천 Wiki를 작성한다. 긴 논문만 문단·문장 경계에 따라 여러 페이지를 함께 묶고, 조각 결과도 한도에 들어가면 바로 최종 종합한다. 고정 페이지 단위·6개 단위 중간 종합은 사용하지 않는다. 원문 offset과 정확한 인용 검증을 유지하며 단일 근거가 한도를 초과하면 내용을 조용히 생략하지 않고 실패를 표시한다.

선택한 LLM_LIGHT_MODEL은 원문 사실·인용 추출에만 사용한다. 짧은 논문이 기본 모델에만 들어가면 기본 모델 1회를 우선한다. 주제 종합·특화 해석·답변·내용 lint는 기본 모델을 유지한다. 기존 유효 Wiki는 재사용하므로 코드를 바꾸었다고 전체 지식을 다시 만들지 않는다. 역할별 환경변수, tokenizer와 출력 한도, 실제 모델 검증의 한계는 [사내 적용 안내 9절](HANDOFF.md#9-논문-길이에-따른-wiki-구성과-경량-모델)을 따른다.

## 인용 검증과 표기 차이

`backend/quote_matching.py`는 Wiki 생성, claim 가져오기, 답변의 직접 인용, LLM lint가 공유하는 인용 비교기다. 먼저 공백만 정리한 원문을 검사하고, 없을 때만 아래의 제한된 표기 정규화를 적용한다. 비교는 로컬에서 수행하며 추가 LLM 호출이나 자동 재생성은 하지 않는다.

- `require-\nment` 같은 실제 줄바꿈 안의 단어 하이픈은 연결을 허용한다. `thin-\nfilm`의 하이픈을 유지하는 인용도 허용한다. 숫자 범위, 짧은 단위, 일반적인 문장 중간의 하이픈은 삭제하지 않는다.
- 영문 단어 안의 U+2010/U+2011 하이픈, `ﬁ`/`ﬂ` 같은 합자, canonical Unicode 문자 조합, 영문 apostrophe와 곡선 큰따옴표를 처리한다. 단어 안의 soft hyphen·zero-width space·BOM도 비교 시에만 무시한다.
- 등록된 단위 앞의 공백(`100 mA`/`100mA`, `25 %`/`25%`)만 정리한다. 단위 변환·대소문자 변환·숫자 사이 공백 삭제는 하지 않는다.
- 수치·유효숫자·지수·단위·부등호·minus/en dash/em dash는 변경하지 않는다. 직접 인용의 `10²`→`102` 또는 `10^2`, `mA`→`A`, `µA`→`μA`, `>`→`≥`는 거부한다. 설명문의 scientific notation과 직접 인용의 규칙은 구분한다.
- 요약, 번역, OCR 추측 교정, `[12]` 등의 중간 문구 생략, 비연속 구절 연결은 허용하지 않는다. 편집 거리·임베딩 유사도로 인용을 승인하지 않는다.

정규화된 문자에서 원문 위치로 역매핑하여 **원래 원문 문자열과 offset**을 저장한다. 후보가 여러 곳이면 임의로 첫 위치를 선택하지 않는다. 이미 저장된 인용과 원문의 대응을 검사하는 구조 lint는 여전히 완전 일치를 요구하며, 문서가 바뀌었다고 인용 위치를 자동으로 재배치하지 않는다.

작업 현황의 Wiki 작업 내역과 처리 카드에는 오류 원인·조치 안내·paper ID·페이지·근거 ID가 표시된다. LLM lint의 실패는 점검 결과의 issue와 code에 기록된다.

| 코드 | 의미와 조치 |
|---|---|
| `quote_not_found` | 원문에 없는 인용. 수치·단위·부등호, 생략·번역 여부를 확인한다. |
| `quote_ambiguous` | 여러 위치에서 발견. 인용에 앞뒤 문맥을 포함한다. |
| `quote_wrong_evidence` | 다른 제공 근거에서 발견. ID 연결을 수정한다. 시스템이 자동으로 출처를 변경하지 않는다. |
| `quote_boundary` | 인접한 페이지/조각의 경계를 가로지름. 근거별로 인용을 나눈다. 두 조각을 연결해 검사하는 것은 오류 진단용이며 인용 승인에는 사용하지 않는다. |
| `quote_too_short` | Wiki·답변의 원문 인용이 12자 미만. 문맥을 추가한다. |
| `quote_empty` / `quote_invalid` | 인용 누락 또는 문자열 형식 오류. |
| `quote_source_changed` | 구조 lint에서 저장된 원문 문자열·offset의 불일치 발견. 원천 근거 확인 후 Wiki를 갱신한다. |

잘못된 인용이 있으면 해당 Wiki 발행은 중단하고 기존 문서를 보존한다. 한 작업에서 이미 성공한 다른 문서까지 되돌리지는 않는다. 이전 실패 내역의 오류 문구는 소급 변경하지 않으며, 업데이트 후 갱신을 요청한 작업부터 새 진단을 기록한다. 공통 지침/작업 프롬프트 변경은 다음 관련 갱신 시 해당 캐시 서명에 반영되므로 재작성 비용이 발생할 수 있다.

회귀 테스트는 `tests/test_quote_matching.py`와 Wiki 저장·작업 현황·lint 통합 테스트에 포함되어 있다. 운영 DB·Wiki와 격리해서 실행하려면 `python -m backend.diagnostics --steps unit`을 사용한다. 긴 문장·표·다단 편집의 추출 순서 문제나 모든 Unicode 변형을 자동 복구하는 기능은 아니다.

## 실패한 작업의 재시도

**작업 현황 → Wiki 작업 내역 → 실패한 작업의 재시도**로 선택한 작업만 다시 대기열에 넣는다. 기존 `refresh_wiki` 권한(관리자)을 유지한다. 완료·대기·진행 중인 작업에는 재시도 버튼을 표시하지 않으며, 실패 기록은 최근 성공 기록보다 우선 보여준다.

- 기존 작업 ID와 `scope`/`expert_id`를 유지한다. 다른 실패 작업을 일괄 재실행하거나 공통 Wiki 전체 갱신 요청을 새로 만들지 않는다. 실제 처리는 기존 worker가 수행한다.
- PDF 추출·DB 적재는 다시 실행하지 않는다. Wiki의 입력 서명과 파일 무결성이 같으면 성공한 논문별 Wiki, 긴 논문의 완료된 원문 조각, 공통 주제·전문가 Wiki를 재사용한다. 실패한 단계와 아직 끝나지 않은 후속 단계를 이어서 처리한다.
- 원천 논문·claim·전문가 범위·작성 지침·모델 등 입력이 실제로 바뀌었다면 해당 문서는 일반 갱신 규칙을 따른다. 이때 이전 결과를 무조건 성공 처리하여 오래된 근거를 사용하지 않는다. 수동으로 편집한 파일은 덮어쓰지 않고 기존 무결성 오류를 표시한다.
- 중복 클릭은 같은 대기/진행 작업을 반환하며 새 작업을 만들지 않는다. 화면에서 본 실패 시점과 최신 실패 시점이 다르면 재시도를 거절하여 오래된 요청이 새 실패까지 자동 재실행하지 않도록 한다.
- 실행 기록과 모델 사용량은 같은 작업에 누적된다. 완료된 문서는 재사용하므로 해당 문서에 대한 추가 LLM 호출·Wiki revision은 만들지 않는다. 재시도에서 다시 실패하면 최신 오류와 재시도 버튼을 표시한다.

API: `POST /api/pilot/wiki-maintenance/jobs/{job_id}/retry`, JSON은 `{"failed_at":"조회한 finished_at 값"}`이다. 과거 기록에 종료 시각이 없다면 `null`을 전달한다. `202` 응답의 `job_id`는 원래 ID이며 `already_requested`는 중복 요청 여부다. 완료된 작업·변경된 실패 시점·삭제/중지된 전문가는 `409`, 없는 작업은 `404`, 권한 없는 사용자는 `403`이다. 기존 전체 재시도 API `/wiki-maintenance/retry`는 계속 폐기 상태(`410`)로 유지한다.

### 실패한 작업 모두 재시도

작업 현황의 **실패한 작업 모두 재시도 (N)** 버튼은 관리자에게 표시된다. N은 화면에 보이는 최근 12개가 아닌 DB 전체의 실패 작업 수다. 성공·대기·진행 중인 작업은 변경하지 않으며, 기존 작업 ID·범위·실행 이력을 유지한다. 기존 worker가 대기열을 처리하고 입력이 같은 완료 문서를 재사용하므로 겹치는 실패 작업도 성공한 원천 논문·공통 주제 Wiki를 다시 생성하지 않는다. PDF/DB ingest는 실행하지 않는다.

삭제·사용 중지된 전문가의 작업은 실패 상태를 유지하고 제외 건수를 표시한다. HTTP 요청은 짧은 트랜잭션에서 대기열 상태만 변경하며 LLM이나 파일 작업을 수행하지 않는다. 처리 중에는 개별·일괄 재시도 버튼의 중복 요청을 막는다.

API: `POST /api/pilot/wiki-maintenance/jobs/retry-failed`, JSON은 `{"failure_snapshot":"/processing의 wiki_retry.snapshot"}`이다. 서버는 전체 실패 작업의 ID·종료 시각을 해시한 snapshot을 트랜잭션 안에서 다시 확인한다. 조회 후 실패 목록이 바뀌거나 같은 요청이 반복되면 `409`로 거절하고 최신 상태를 조회한다. 새로 실패한 작업을 오래된 요청으로 다시 실행하지 않는다. 유효한 요청은 `202`와 `queued_count`, `queued_job_ids`, `skipped`를 반환한다. 실패 작업이 없으면 0건으로 끝난다. 종전 `/wiki-maintenance/retry` API를 다시 활성화하는 기능은 아니다.

## 토큰 비용을 해석하는 방법

용어 사전은 공통 지침에 더하는 별도 편집 규칙이다. 입력에 등장하는 승인 항목만 최대 24개/6,000자로 제한하여 compile·답변·lint에 전달한다. 수정 시 전체 Wiki 재생성이나 embedding 재계산을 요청하지 않는다. 다음 관련 Wiki 갱신에서 선택된 용어 fingerprint로 재작성 여부를 판단하고, 답변 trace에는 당시 사전 버전과 적용 항목을 보존한다. 인용·수치·단위 및 기존 수동 문서는 사전의 정규식 치환 대상이 아니다. 상세 내용은 [용어 지침](TERMINOLOGY.md)을 참고한다.

주요 비용은 최초 원문 분석, 주제별 종합, 변경에 따른 재종합, 질의 답변, 내용 lint에서 발생한다. 전문가별로 원문 전체를 다시 읽지 않으며 목차와 링크 갱신에는 LLM을 사용하지 않는다. 변경이 없는 종합 입력은 재사용하고, 질문에는 선택한 Wiki 부분·claim·원문 구절만 전달한다. 정기 lint는 기존 호출·본문 예산을 유지한다.

공통 지침도 매 요청 입력의 일부이므로 토큰을 사용한다. 입력 문자 수는 token 수가 아니며, 정확한 사용량은 사내 모델의 tokenizer 또는 API가 제공하는 usage로 확인해야 한다. 현재 API 미연결 상태에서 비용 절감률이나 전체 구축 token을 측정했다고 주장하지 않는다. 공통 지침 변경은 여러 문서에 영향을 주므로 문구를 자주 바꾸어 불필요한 재작성을 유발하지 않도록 한다.

생성·갱신 job의 실측 모델명·호출·입출력 token·소요 시간은 **작업 현황 → Wiki 작업 내역**에서 확인한다. 기본/경량 모델을 구분하고 모델별 수행 단계와 응답 시간도 제공한다. usage가 없는 API 응답은 미제공, 일부만 확인되면 일부 합계로 표시하며 과거 작업을 소급 추정하지 않는다. DB의 wiki_job_runs와 wiki_model_calls에 저장하고 네트워크 호출 중 쓰기 잠금을 유지하지 않는다. 별도 정기 lint·질의·embedding·reranker는 이 집계에 포함하지 않는다. 시간·token 해석과 기존 DB 적용 절차는 [사내 적용 안내 10절](HANDOFF.md#10-wiki-작업별-모델-사용량)을 따른다.
