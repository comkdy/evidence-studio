# 근거를 종합하는 연구 QA

2026-10-13. 이 문서는 [DB 구성](DATABASE_PLAN.md)과 연결되는 현재 구현이다. 모델 응답·검색 품질을 개선할 수 있는 실행 경로와 검증 수단을 제공하며, 사내 모델의 과학적 정확도 향상을 실측했다고 주장하지 않는다.

## 저장·검색의 역할

PDF·claim·measurement·condition은 원천 근거를 보존한다. Wiki는 공통 종합이며 독립적인 사실 원장이 아니다. 전문가는 담당 범위와 설명 관점을 제공한다. 전문가를 추가해도 논문을 재추출하지 않는다.

검색은 선택한 활성 전문가들의 담당 논문 합집합 안에서 수행한다. 전체 라이브러리로 자동 확장하지 않는다. 종합 판단은 합집합 근거를 사용하고, 전문가별 관점에는 그 전문가가 담당하는 근거 ID만 허용한다. 개인정보·접근 권한은 전문가의 관심 분야와 별개이며, 향후 자료별 ACL을 도입하면 검색과 원천 확장 양쪽에 적용해야 한다.

한국어 전문 용어는 공통 용어집으로 확장한다. 키워드·vector 결과를 RRF로 합치고 설정된 reranker를 적용한다. 근거 조립에서는 직접 검색된 claim·원문을 우선하고, 같은 논문의 반복에 제한적인 순위 패널티를 적용한다. 낮은 검색 순위의 논문을 다양성만을 위해 맨 앞으로 올리지 않는다. Wiki는 남은 예산에 본문과 연결 원천 claim·수치·조건·인용 구간이 모두 들어갈 때 함께 채택한다. 들어가지 못하는 Wiki의 의존 근거가 직접 검색된 핵심 근거를 밀어내지 않는다. 현재 연결은 문서 수준이며 문장별 과학적 지지를 보증하지 않는다.

원문 passage는 기존 parent 문맥을 정확한 페이지별 offset으로 확장한다. parent가 없거나 손상되었거나 예산에 들어오지 않으면 원래 검색 구간을 유지하고 문맥 한계를 기록한다. 조건이 포함된 claim은 자르지 않는다. 검색 중복 수와 독립적인 연구 수를 혼동하지 않는다.

## 단일 심층 질의 흐름

`POST /api/pilot/ask`는 `{question, expert_ids}`로 요청한다. 모든 새 질문은 심층으로 처리하며 화면의 모드 선택은 제거했다. 이전 클라이언트의 명시적 `mode: "deep"`은 허용하지만 `basic` 등 다른 값은 422로 거절한다. 과거에 저장된 답변의 모드·본문·실행 기록은 변경하지 않는다.

화면에서는 **질문하기** 한 번으로 시작한다. 기본인 전문가 자동 선택은 추천 결과의 활성 전문가를 최대 2명 골라 바로 답변 요청으로 이어지고, 직접 선택은 지정한 전문가에게 바로 요청한다. 자동으로 고를 전문가가 없으면 범위를 임의로 넓히지 않고 직접 선택을 안내한다. 추천과 답변은 하나의 취소 가능한 화면 작업으로 처리한다.

- 심층: 계획 → 추가 검색 → 근거 충분성 검토와 보완 검색 → 답변 → 진술별 내용 검토 순서다. 계획·충분성·답변·내용 검토의 LLM 호출은 최대 4회, 원질문 포함 검색 질의는 최대 6개다. 중복 질의는 실행하지 않는다.
- 근거 예산은 48,000자이고, 공통 evidence pool을 전문가별로 복제해서 보내지 않는다. 각 모델 입력은 지침 포함 100,000자 이하다. 이는 token 한도와 같지 않으므로 사내 모델 tokenizer/context에 맞춘 검증이 필요하다.
- 새 작업 시작·LLM 결과 채택 예산은 RESEARCH_TIMEOUT_SECONDS로 설정하며 기본 1,500초다. 각 LLM I/O 대기는 LLM_TIMEOUT_SECONDS(기본 300초)와 남은 예산 중 작은 값으로 제한한다. LLM 호출 슬롯 대기도 전체 예산에 포함하고, 예산 이후 도착한 LLM 결과는 사용하지 않는다. 이미 시작된 embedding/reranker 호출과 socket 읽기는 별도 timeout을 사용하므로 엄격한 전체 wall-clock 상한은 아니다. 추천 처리는 답변 예산과 별도이며 스트림에서는 같은 요청 안에서 먼저 수행한다.
- 지침은 작업 시작 시 고정한다. 지침 부재·잘못된 응답·검토 실패·예산 소진 시 실패를 숨기지 않고 확인 가능한 검색 근거를 제공한다. 사내 LLM 미설정 상태를 생성된 답변으로 표시하지 않는다.

응답은 기존 `claims`, `hits`, `answers`, `note` 외에 `synthesis`, `research`, `run_id`를 포함한다. `claims/hits`는 검색해서 검토에 제공한 근거 목록이며 모두가 최종 답변에 인용됐다는 뜻은 아니다. 실제 사용 근거는 문장 인용과 실행 기록에 있다. `research`는 mode·queries·rounds·paper_count·limitations·validation_status를 제공한다.

## 검증과 불확실성

답변 문장은 논문 근거(finding), 종합 해석(synthesis), 검증 전 가설(hypothesis), 제안 실험(proposal)로 구분한다. 제목은 중립적인 목록으로 제한해 검증되지 않은 결론이 제목으로 빠져나가지 못하게 한다.

모든 문장에 claim/source_text 원천 인용이 필요하다. Wiki 단독 인용을 거부하며 source_text는 정확한 인용구를 요구한다. finding/synthesis는 인용한 원천에 존재하는 숫자 값과 지원하는 단위 조합을 대조한다. 현재 지원 단위는 주요 시간·전압·전류·에너지·전력·온도·백분율·길이 표현이다. 임의 계산값을 논문의 결과로 추가하지 않는다. proposal의 새 실험 설정값은 허용하되 미검증 제안으로 표시한다.

이 검사는 숫자의 올바른 대상·부등호·표의 행/열·조건 비교·인과관계를 모두 증명하지 않는다. 심층의 별도 모델 검토가 이를 추가 확인하지만 역시 사람 검토를 대체하지 않는다. 심층 검토가 일부 문장을 거부하면 해당 종합/전문가 답변 전체를 보류하여 남은 문장만으로 잘못된 결론을 만들지 않는다.

근거·전문가 설정·Wiki가 답변 준비 중 변경되면 409로 재질의를 요청한다. 판단을 위한 자료가 부족하거나 사람 검토 대기, 미기재 조건, OCR 누락이 있으면 한계를 표시한다. 실험 제안에서는 대립 가설·대조 조건·관측값·결과별 해석과 팀 장비/공정 정보 부재를 고려한다.

## 실행 기록과 배포

기존 스키마를 유지하며 `answer_runs`만 추가한다. 서버 시작의 `initialize()`가 idempotent하게 적용한다. 원천 claim·수치·조건·Wiki를 변환하거나 삭제하지 않는다. 운영 DB 변경 전 온라인 백업을 권장한다.

질문·모델 식별자·지침 hash·검색 순위와 제외 이유·전문가/논문 hash·당시 evidence·생성/게시 결과·지연·API가 반환한 token usage를 불변 snapshot으로 저장한다. API가 usage를 제공하지 않으면 사용량을 추정값으로 채우지 않는다. 단계별 소요 시간과 LLM 호출별 대기 포함 elapsed_ms·입력 문자 수도 기록한다. 서비스 주소·키·인증 쿠키는 기록하지 않는다.

`GET /api/pilot/answer-runs/{run_id}`와 그 아래 `/claims/{claim_id}`는 **요청 소유자만** 조회할 수 있다. 관리자도 다른 소유자의 기록을 조회할 수 없다. 답변의 claim 인용은 당시 snapshot을 열고 Wiki 인용은 revision을 고정한다. 원본 DB 교정 후에도 snapshot은 바뀌지 않는다.

이 기록은 Wiki·검색 색인의 입력이 아니며 팀 공유 사실로 승격되지 않는다. 브라우저 대화 목록·공개/비공개·휴지통은 현재 사번별 로컬 저장 방식이다. 브라우저의 대화 삭제가 서버의 실행 snapshot을 삭제하는 것은 아니다. 서버 보존 기간·삭제 정책·다중 사용자 대화 동기화는 후속 운영 설계가 필요하다.

공통 topic은 tag별 안정적인 root를 유지하고 입력이 많으면 6개 이하의 하위 종합으로 연결한다. 내부 `topic_part`는 검색·일반 목록에서 제외한다. 기존 수동 본문은 보존하고 필요한 변경만 새 revision을 만든다. 신규 source에는 선별 범위와 검토 상태를 명시하며, 미변경 source 전체를 단지 문구 개선을 위해 재분석하지 않는다.

## 평가 및 남은 범위

`python -m unittest discover -s tests -p 'test_*.py'`와 `node --test tests/*.test.mjs`, `pnpm build`로 회귀를 확인한다. 신규 테스트는 범위 합집합/격리, Wiki의 원천 동반, parent 문맥, 예산, 추가 검색, 숫자·단위·잘못된 모델 응답, 검토 실패, 근거 변경, 기록 소유권과 snapshot을 다룬다. 테스트 모델의 성공은 실제 과학적 답변 품질을 뜻하지 않는다.

[검색 비교 평가 도구](RESEARCH_EVALUATION.md)는 원문만/구조화 근거 추가/Wiki 추가를 같은 조건으로 비교한다. 실제 팀 질문과 전문가가 검토한 정답 근거를 넣어야 한다. 종합 답변 자체는 별도로 중요한 반례·조건·인용의 지지 관계·판단 유용성을 사람 평가해야 한다.

PostgreSQL/ANN 전환, 논리적 논문과 PDF 버전 분리, claim/measurement 자체의 revision·철회, 범용 수치 ontology, 자동 SQL 추출, 표·그림 OCR, 팀의 내부 실험 자료는 이번 QA 변경으로 구현된 것이 아니다. 현재의 근거 snapshot과 검색 평가를 바탕으로 이어서 확장한다.

## 이어지는 대화·진행 상태·중지

첫 화면부터 대화 영역과 여러 줄 메시지 입력창을 표시한다. 첫 전송은 **대화 시작**, 다음 전송은 **이어서 질문**이며 입력창에서 **답변 중지**를 실행한다. Enter는 전송, Shift+Enter는 줄바꿈이다. 한국어 IME 조합 중 Enter는 전송하지 않는다. 이전 대화를 다시 열면 같은 대화에 질문을 덧붙인다.

로컬 Vite 개발·미리보기의 API proxy는 `changeOrigin: false`로 브라우저가 보낸 Host를 유지한다. 4173 화면에서 8011 API로 전달할 때 Origin과 Host가 달라 질문 POST가 403으로 차단되는 문제를 방지한다. 서버의 동일 출처 검사 자체는 유지한다. 사내에서는 FastAPI가 제공하는 동일 출처 화면 또는 Host/프로토콜을 올바르게 전달하는 사내 프록시를 사용한다.


화면은 `POST /api/pilot/ask-stream`에 `question`, `expert_ids`, `selection` (auto/manual), `history_run_ids`를 보낸다. 응답은 NDJSON이며 `progress` (stage/message), `experts` (ids/names), `result` 또는 `error` 이벤트다. 빈 줄은 연결 유지용 heartbeat다. 프록시에서는 buffering을 끄고 답변 제한 시간보다 긴 read timeout을 설정한다. 기존 `/ask` JSON 응답 API도 유지한다.

최근 완료 답변 최대 6개를 본인 소유인지 확인한 뒤 문맥으로 사용한다. 서버는 각 이전 질문 최대 1,000자·답변 최대 2,200자만 가져온다. 클라이언트가 보내는 임의의 과거 답변 본문은 신뢰하지 않는다. 계획·보완 검색·답변·검토에 대화 문맥을 전달하되 논문 근거와 분리하고, 후속 질문도 현재 전문가 범위에서 원천을 새로 검색한다. 질문의 대명사와 생략된 주제 해석을 위해 최근 질문의 주제를 검색에도 보충한다.

진행 표시는 실제 실행한 문맥 확인·전문가 선택·검색·claim/수치/조건 조립·답변 작성·인용 검토·최신 상태 확인 단계다. 가짜 진행률이나 모델의 내부 추론을 표시하지 않는다. 최종 답변은 근거 검토를 마친 뒤 제공하며 검증 전 토큰을 바로 내보내지 않는다.

중지 버튼·페이지 이동·새 대화 시작은 fetch를 abort한다. 서버는 연결 종료를 감지하고 단계 사이와 모델/검색 반환 후 취소 여부를 확인하여 이후 작업과 답변 저장을 중단한다. 이미 실행 중인 외부 HTTP 요청은 해당 API의 반환 또는 timeout까지 계속될 수 있고 제공자의 연산·과금을 취소한다고 보장하지 않는다. 완료가 중지보다 먼저 저장된 경우 서버 snapshot이 남을 수 있다. 취소 상태도 브라우저 대화에 남아 이어서 질문할 수 있다.

한 서버 프로세스당 스트림 작업은 최대 4개다. Wiki·lint·기존 JSON 질의 API도 공유하는 실제 LLM 호출 한도는 LLM_MAX_CONCURRENT_REQUESTS(기본 2개)다. 대기는 FIFO이며 최대 LLM_QUEUE_TIMEOUT_SECONDS(기본 300초) 또는 남은 답변 예산까지다. 대기 중 취소하면 HTTP를 보내지 않으며, 이미 보낸 호출의 slot은 반환/timeout 전까지 유지한다. 대기·모델 생성 상태를 구분해 표시한다. timeout/HTTP 408·504 또는 혼잡/HTTP 429·503이 발생한 질문은 후속 LLM 단계를 더 호출하지 않고 확보한 근거와 실패 사유를 반환한다. 이는 프로세스 내 과부하 방지이며 분산 작업 큐가 아니다.

이전 단일 질문 기록은 한 턴의 대화로 다시 열 수 있다. 브라우저가 닫혀 남은 pending 기록은 재개 중인 것처럼 표시하지 않고 중단 상태로 복원한다. 대화 목록·공유 표시는 브라우저 저장이며 실제 사용자 간 동기화는 별도 범위다.

회귀 테스트는 `tests/test_conversation.py`와 `tests/research-conversation.test.mjs`에서 문맥 전달·소유권·진행 순서·연결 종료·중지 후 후속 호출 방지·UTF-8 스트림 조각·과거 기록 호환을 확인한다. 기존 연구 QA 테스트의 근거·수치·권한 검증은 유지한다.
