# 사용자와 로그인 연결

2026-10-13. 현재는 임시 관리자 자동 접속을 사용한다. 실제 사내 SSO와 사용자 프로필 API는 아직 연결하지 않았다.

## 권한

| 권한 | 관리자 `admin` | 슈퍼 유저 `superuser` | 일반 유저 `user` |
|---|---|---|---|
| 질의·논문·Wiki 열람·개인 페이지 | 가능 | 가능 | 가능 |
| 전문가 생성·수정·삭제·복원 | 가능 | 가능 | 불가 |
| 특화 지식 생성 요청 | 가능 | 가능 | 불가 |
| 공통 Wiki·전문가별 Wiki 수동 갱신 | 가능 | 불가 | 불가 |
| 유저 등록·권한 변경·사용 중지 | 가능 | 불가 | 불가 |

프런트엔드는 `/api/auth/session`의 권한으로 메뉴를 표시한다. API는 요청마다 인증하고 변경 작업은 서버에서 권한을 검사한다. 클라이언트가 보내는 role·사번 헤더는 실제 권한 근거가 아니다. 공통 정책은 `backend/auth.py`에 있다.

Wiki 수동 갱신은 `refresh_wiki` 권한으로 분리했다. 전문가 설정에서 관리자에게만 공통 Wiki 갱신과 각 전문가 카드의 Wiki 갱신 버튼을 표시한다. 일반 유저·슈퍼 유저는 관련 실행·작업 상태 API를 직접 호출해도 403이다. 전문가 지식 열람 화면에는 갱신 버튼을 두지 않는다.

**신규 사용자는 첫 SSO 접속 시 자동 등록한다.** 쿠키 검증으로 사번을 확인하고 사내 프로필 API로 이름·팀을 조회한 뒤, DB에 없는 사번이면 일반 유저로 생성한다. 별도의 회원가입·관리자 등록·승인은 필요하지 않다. 재접속은 동일 사번의 계정을 재사용하고 기존 역할·사용 중지 상태를 유지한다. 인증 또는 프로필 조회 실패 시 미완성 계정을 만들지 않으며 다음 접속에서 다시 시도한다.

관리자는 자동 등록된 유저의 역할과 이용 상태를 관리한다. 선택 기능인 '사전 권한 지정'으로 첫 접속 전 특정 사번의 역할을 미리 정할 수도 있다. 이름·팀은 사내 프로필에서 동기화한다. 동일 계정의 동시 편집은 revision으로 확인하고, 마지막 활성 관리자 제거와 본인의 권한 변경·사용 중지는 거부한다. 역할·상태 변경은 `user_audit`에 기록한다. 사용 중지는 기존 지식을 삭제하지 않는다.

## 초기 관리자

- DB 초기화 시 `.env`의 `BOOTSTRAP_ADMIN_EMPLOYEE_ID`을 관리자 권한으로 최초 한 번 등록한다. 재시작·프로필 동기화가 기존 권한이나 사용 중지 상태를 덮어쓰지 않는다.
- 이름과 팀은 미확인 값으로 유지하고 화면에는 '임시 관리자', 'SSO 연결 후 표시'로 안내한다.
- `AUTH_MODE=local_admin`이면 비밀번호·쿠키 없이 이 계정으로 접속한다. 로컬 확인용 모드이므로 사내 운영 전 `sso`로 전환한다.

## 사내 연결

```text
SSO 쿠키 → backend에서 진위·유효기간 검증 → 검증된 사번
  → 신규 사번: 이름·팀 조회 → 일반 유저로 DB 자동 등록 → 개인 페이지
  → 기존 사번: 기존 역할·사용 상태 확인 → 개인 페이지
```

`backend/sso_adapter.py`의 두 함수를 실제 계약에 맞게 구현한다.

1. `verify_sso_cookie(cookie) -> employee_id`: 인증 서버로 검증하거나 계약에 따른 서명·issuer·audience·만료 검사를 수행한다. 유효하지 않으면 401을 반환한다. 쿠키에서 사번을 단순 파싱하는 것으로 인증을 완료하지 않는다.
2. `fetch_employee_profile(employee_id) -> EmployeeProfile`: 검증된 사번으로 사내 API를 호출하여 사번·이름·팀을 반환한다. 응답 사번은 입력과 같아야 한다.

요청/응답 형식이 미확정이므로 현재 두 함수는 명시적인 503을 반환한다. 주소·키·쿠키 원문은 프런트엔드·DB·로그에 노출하지 않는다. 프로필은 1시간 캐시하고 역할·사용 상태는 매 요청 DB에서 확인한다. 사전 등록하지 않은 인증 사용자는 일반 유저로 등록한다. 설정된 초기 관리자의 첫 SSO 접속에는 기존 관리자 역할이 이어진다.

`.env`에서 `AUTH_MODE=sso`, `SSO_COOKIE_NAME=<실제 쿠키 이름>`을 지정한다. SSO 모드는 누락·미구현·인증 실패 시 접근을 차단하고 임시 관리자로 우회하지 않는다. 쿠키 domain/path/Secure와 앱 도메인, 프록시 신뢰 헤더는 사내 환경에 맞게 확인한다. 변경 요청은 같은 Origin만 허용하며 SSO 모드에서 Origin 누락도 거부한다. SSO 로그아웃·리다이렉트는 서비스 계약 확정 후 연결한다.

권한·요청 출처 검사의 기준: [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## 개인 페이지와 저장 범위

사번·이름·팀·권한·접속 방식과 내 질문·비공개·휴지통·북마크를 표시한다. 새 질문의 요청·공개 범위·진행 상태는 서버에서 소유자별로 보관한다. 대화 묶음 100개와 북마크는 브라우저에 사번별 key로 보관한다. 계정이 바뀌면 해당 사용자의 상태로 다시 읽으며, 소유자가 없는 북마크는 자동으로 다른 계정에 가져오지 않는다.

팀 공유는 새 질문의 서버 공개 범위를 변경한다. 공유한 질문·답변·해당 인용은 팀에서 볼 수 있지만 개인 answer run과 보고서는 계속 소유자만 조회한다. 이전 대화나 보고서 문맥이 있는 질문은 비공개로 제한한다. 비공개 질문은 지속 개선 수집에서 제외하며 공유 철회도 서버에서 반영한다. 대화 묶음·북마크의 동기화와 보존/삭제 정책은 별도 운영 범위다. 임시 모드는 모든 접속이 같은 계정이므로 사내에 공개 배포하지 않는다.

## 검증

테스트 의존성은 `backend/requirements-dev.txt`다. `python -m unittest discover -s tests -p 'test_*.py'`로 초기 관리자, SSO 실패 차단, 프로필·권한 분리, 권한별 접근 제한, 변경 충돌과 요청 출처 검사를 확인한다. 실제 사내 인증 검증은 연결 후 수행한다.
